## Fixed automatically (shipped + re-verified)

### 🔴 CRITICAL-1 — Cross-account data leak via foreign-key injection → PDF  (v0.23.6)

**The breach.** As account **A**, create an invoice with **B's** `client_id`; download the PDF as A.
The PDF rendered **B's client in full** — company name, contact, address, email (and, from the same
unscoped fetch, VAT and bank details). Proven end to end:

```
A (user c374…) → POST /invoices {client_id: <B's client>}  → 201
A → GET /invoices/<id>/pdf  → 200, PDF text contained:
   ZZ-AUDIT-B-CLIENT-1  ZZ-AUDIT-B-PERSON-1  ZZ-AUDIT-B-ADDR-1  Leeds LS1 1AA  zzbclient1@example.com
   (client row owned by user 285a… — account B)
```

**Root cause.** Two layers, both missing the one boundary the whole system has (`user_id`):
1. **Write side** — `create/update invoice`, `create payment`, `create/update expense` accepted a
   foreign `client_id` / `invoice_id` / `category_id` / `item_id` with no ownership check.
2. **Read side** — the PDF and the send routes fetched the client with
   `select(Client).where(Client.id == invoice.client_id)` — **unscoped by `user_id`**.

**Fix.** Added `app.api.deps.assert_owned()` (404s a reference that isn't the caller's) and wired it
into every write that carries a foreign key; scoped the PDF/send client fetch by `user_id` as
defence-in-depth. After the fix every cross-account attempt returns **404** and the PDF for a legacy
bad row renders **no** client at all. **Verified in prod**: foreign/unknown FK → 404 on invoices,
payments and expenses.

### 🔴 CRITICAL-2 — Cross-account leak via unscoped report joins  (v0.23.7)

**The leak.** `/reports/` "revenue by client" and "expenses by category" `LEFT JOIN` the name tables
on **id alone**. An A row carrying B's `category_id` made A's report render **`ZZ-AUDIT-B-CAT`** —
another account's category name — and the client join was the same latent bug (only quiet because the
cross-ref invoices were drafts, which the report filter excludes).

**Fix.** Scoped both joins in their `ON` clause (`Client.user_id` / `ExpenseCategory.user_id == caller`)
so a foreign reference collapses to the existing "Unknown Client" / "Uncategorised" fallback instead of
leaking a name. Re-verified: B's marker gone from A's reports; category shows "Uncategorised".

> With v0.23.6 blocking foreign FKs at write time, no *new* cross-ref can arise; v0.23.7 guarantees
> even a legacy row cannot leak a name. Both layers now hold.

### 🟠 MEDIUM-3 — Money serialised as strings on `/admin/*`  (v0.23.8)

`/api/v1/admin/metrics` and the **public** `/api/v1/admin/donations` returned money as **strings**
(`"400.00"`) — the exact regression the `Money` type exists to prevent (a client then does string
arithmetic). Bare `Decimal` in the inline response models; `/sys/metrics` already used `Money` and was
correct. Switched the three response fields to `Money`. **Verified in prod**: now numbers.

### 🟠 MEDIUM-4 — Out-of-range input returned 500; unvalidated send recipient  (v0.23.9)

- A value overflowing its column (15-digit amount into `numeric(12,2)`, tax past `numeric(5,2)`, a
  5 MB string) reached asyncpg as a data exception and surfaced as a **bare 500**. `get_db` now maps
  SQLSTATE class **22 → 422** and class **23 → 409**, re-raising everything else; the mapped responses
  pass back out through CORS so the page can read them. **Verified in prod**: overflow → 422 with
  `Access-Control-Allow-Origin` present.
- `SendInvoiceRequest.email` was a bare `str`, so `victim@x\nBcc: evil@x` reached mail construction
  (header-injection shape). Now `EmailStr` — the newline is rejected at the edge.

### 🟠 HIGH-5 — Duplicate invoice/payment numbers under concurrency  (v0.23.10)

**Repro (was reproduced LIVE in production).** 10 simultaneous `POST /invoices/` as one account:

```
local : INV-26-00015 issued 4×   (double-click Save → two identical numbers too)
prod  : 10 creates → 3 distinct numbers (…00008 ×2, …00009 ×5, …00010 ×3)
```

`invoice_number` has only a **non-unique** index; `payment_number` has **no** index. The number is
derived from `max(existing)+1` / a counter column with **no lock and no unique constraint**, so
concurrent transactions read the same value between `SELECT` and `INSERT`. Prod was worse than local
because four workers widen the window.

**Fix.** `app.core.locks.lock_user_numbering()` — a transaction-scoped Postgres advisory lock keyed on
the account — is taken at the top of both number generators, so a second concurrent create waits until
the first commits and reads the already-incremented value. Different accounts never block each other.
The mark-as-paid path, which built its number from `count(*)+1` (a different, reuse-prone scheme), now
routes through the same generator. **Re-verified in prod**: 12 simultaneous creates → 12 distinct
sequential numbers, no duplicates, no errors; double-submit → two distinct numbers.

> **Follow-up (v0.23.14):** the belt-and-braces unique constraint `(user_id, invoice_number)` was
> added after all, at the owner's request — migration `b4c5d6e7f8a9`, which uniquifies any pre-existing
> duplicate first (a no-op locally and across the prod audit accounts) so it can never fail the deploy.
> The DB now rejects a duplicate outright; the advisory lock means normal and concurrent creates never
> trigger it (verified in prod: 12 concurrent → 12 distinct numbers, no IntegrityError). Payment numbers
> keep the advisory-lock protection; a matching payment constraint can be added the same way.

### ℹ️ Design notes (not defects)

- A **captured access token replays after logout** and for ~30 min after a user is deactivated —
  access tokens are stateless with no revocation list. Consistent, documented; raise only if you want
  server-side revocation.
- Rate limits are **per-worker in memory**, so the real allowance ≈ 4× the coded number in prod. This
  is honest and documented; measured live (~20 for the forgot-password limit of 5).
